## 二、自然语言确认通道：结构性缺口与决策记录

**问题位置**：`src/engine/schema.ts` 的 `confirmations[]{field,value,input_version}`（D60）、`src/engine/ops/schema.ts` 的 `UI_OP_TYPES`（D29 白名单 7 项 + 流程操作 3 项）、`src/engine/evaluate.ts` 的输入版本从 v1 起算。

**现状**：D60 规定「早于当前输入版本的确认一律标需重新确认」，但白名单里没有「写入确认记录」的操作，D58 又禁止界面使用 `PATCH`。因此在一个 `evaluate` 会话内无法为用户刚确认的字段追加 `confirmations[]`：`evaluate` 总是从 v1 起算，会话内新增的确认要么写不进输入，要么版本对不上。

**已采用的保守处理（本轮实现）**：把确认记录当作**案例输入的一部分**在进入引擎前一次性形成。`src/nl` 的 `buildConfirmedCase()` 用引擎 `caseFileSchema` 复验后返回新的案例输入（`confirmations[]` 的 `input_version` 为该案例代表的版本，即 `v1`），再调用 `evaluate(case, [], DEMO_CFG_1)`；不新增 Op、不使用 `PATCH`（D58）。这样：合法确认数据确实能进入正式计算，`userConfirmations` 状态为 `CURRENT`；输入一旦变化（任何改变版本的操作），旧确认自动变 `NEEDS_RECONFIRM`，与 D60 一致。已由 `tests/unit/nl.test.ts` 的 12 条链路覆盖。

**仍未解决的取舍（需要团队裁决）**：

- 选项 A（当前实现）：确认只在形成输入版本时写入，会话内的「再确认一个字段」需要重新构造输入。界面表现为「确认后重算一次」。改动最小、不碰规则；代价是交互上多一次重算。
- 选项 B：新增流程操作 `CONFIRM_FIELDS`（写入 `confirmations[]` 并加版本）。需要改 `rules.md` §12.4/D29 与 `UI_OP_TYPES`、补 Schema、枚举、验证器、向量与追溯，属于数据结构变更。
- 推荐 A（保守、可回退）；若最终要支持「边聊边确认」，需团队先批准 B 并同步 `policy_card` 的操作清单。
